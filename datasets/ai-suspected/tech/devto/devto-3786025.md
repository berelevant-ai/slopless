## The Problem We Were Actually Solving

Veltrix is Hytales spatial search overlay: it indexes every tile, loot chest, and mob spawn as a dynamic GeoJSON document, then streams matches to the frontend so the treasure-hunt overlay updates in near real time. Our SLA was 95 % of requests under 400 ms end-to-end. We had shipped it, done the slides, and even run a 100 k concurrent load test in staging—until production traffic hit 1.8 million concurrent hunters during the Skarran launch week.

The failure mode wasnt the query engine itself; it was the handshake between Veltrix and the tile-service. Every time a player mined a wall, the tile-service published a delta, Veltrix indexed it, and the frontend asked for the updated bounding box. Under write-heavy load, Veltrixs Kafka consumer group couldnt keep its lag below the auto-commit threshold. We watched consumer_lag metrics climb from 2k to 480k in 12 minutes and crash the broker disks before the autoscaler even fired. What the documentation glossed over was that Veltrixs default commit interval (1 s) plus a 100 ms processing SLA created a perfect storm when Kafka message.max.bytes was still set to 1 MB—far too large for the micro-delta deltas we were sending. The docs mentioned bytes per second, not the per-message size, and we missed it.

## What We Tried First (And Why It Failing)

Our first reflex was to throw more pods at the problem. We spun up 3× the recommended replica count for veltrix-query pods, each with 2 vCPU/4 GB RAM. The autoscaler ramped to 42 pods, yet the p99 latency stayed flat at 2.1 s. Why? The bottleneck wasnt CPU; it was the Kafka consumers internal poll() loop. Each pod was spending 60 % of its cycles blocking on consumer.rebalance.timeout.ms = 30 s, while the autoscalers cool-down was 300 s. The metrics in veltrix-query showed a mean poll latency of 1.8 s, but the 99th percentile hit 28 s—exactly the rebalance timeout. We tried bumping consumer.rebalance.timeout.ms to 60 s, but that only delayed the OOM: after 4 minutes the JVM heap jumped from 2 GB to 3.2 GB, triggering the pod eviction loop. The garbage collector spent 45 % of CPU in CMS remark pauses, and we still dropped 0.6 % of events. At 1.8 million concurrent users, 0.6 % is 10 800 lost loot notifications—users noticed.

## The Architecture Decision

We ripped the band-aid off the same afternoon. The fix came in two parts:

1. Move the indexing boundary upstream. Instead of letting Kafka deliver raw micro-deltas to Veltrix, we inserted a tiny Go service called delta-batcher in front of the consumer. It runs in front of each veltrix-query pod, batches events per bounding box, and publishes a single GeoJSON delta to a topic that Veltrix ingests. Batch size is 500 events or 100 ms, whichever comes first. We set batch.max.messages = 500 and batch.max.bytes = 16 KB. This gave us a 6× reduction in poll latency (mean now 220 ms) and 99th percentile 1.2 s.

2. Shift the consistency knob. The original design assumed eventual consistency was okay for loot overlays. But hunters reported feeling cheated when an event chest vanished milliseconds after they opened it. We switched Veltrix to read-your-writes by adding a secondary index backed by Redis Streams. After each write to the primary Geo index, we push a 64-byte Redis message with the tile ID and a monotonic clock. The frontend queries Redis first; if the tile version is ahead, it bypasses the async search. That added 8 ms to write path but dropped user complaints from 3 % to 0.1 %.

The trade-off: Redis Streams now sits in the critical path for every loot-chest interaction. We sized it at 8 shards, each with 16 GB RAM, and set stream.trim = true to keep the stream under 1 GB. We also tuned Redis maxmemory-policy to noeviction—wed rather crash the hunt service than lose a chest.

## What The Numbers Said After

One week after the change, we re-ran the same Skarran load test. The results:

- Kafka lag stayed below 5 k events (down from 480 k).
- veltrix-query p99 latency dropped to 340 ms (SLA met).
- Frontend inventory refresh rate stayed under 200 ms for 99 % of players.
- Redis Streams memory usage averaged 640 MB with peaks at 900 MB during burst spawns.
- Cost delta: +12 % on Redis, –8 % on Kafka brokers (fewer partitions to mirror), 0 % on veltrix-query pods (we actually downsized from 42 to 18).

Most importantly, the support tickets about missing loot dropped to zero within 24 hours. The games community manager sent me an email titled Hunt finally happy, which is the highest form of production proof we accept.

## What I Would Do Differently

I would not have shipped the original Veltrix without a load test that included the inventory overlays read-after-write path. The docs suggested it, but the staging environment capped at 300 k users, and the pipeline never simulated the race between mining and loot discovery. Next time we will fork the inventory service in staging and replay production traffic through it for 48 hours
