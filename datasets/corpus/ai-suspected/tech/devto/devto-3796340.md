# I Built a PDF Conversion API So You Don't Have to Install Ghostscript

A developer friend messaged me last month. He's building a SaaS for accountants — small product, growing nicely. One feature his customers kept asking for: *"Can your app just compress these PDFs before I email them?"*

Simple feature on paper. Until he tried to build it.

He spent a weekend on Ghostscript flags trying to get the compression right. Then another evening fighting Docker images because Ghostscript wouldn't install on his Railway deployment. Then he discovered his compressed PDFs sometimes corrupted the text layer, which broke his customers' workflow. Then he realized he'd need OCR for scanned PDFs, which meant Tesseract, which meant another binary, more system dependencies, more Docker pain.

*"This is supposed to be a one-line feature. I've spent four days on it."*

This is the conversation that made us build the ConvertKr API. If you've been down this rabbit hole, you know exactly what he meant.

## What it does

Same PDF and image tools we've been running for free at [convertkr.com](https://convertkr.com), exposed as a JSON HTTP API at `api.convertkr.com`. You send a file in, you get a processed file back. No file storage. No queue infrastructure. No system dependencies to install.

Currently live:

- **PDF** — compress, merge, split, rotate, crop, organize (reorder pages), add page numbers, insert pages, extract text
- **Images** — convert (any format to any format), resize, watermark, HEIC to JPG
- **Coming next** — OCR, HTML to PDF, PDF to image, PDF to Word (Office-grade via Windows VPS), background removal

## The simplest possible example

```bash
curl -X POST https://api.convertkr.com/v1/compress-pdf \
  -H "Authorization: Bearer ckr_live_YOUR_API_KEY" \
  -F "file=@invoice.pdf" \
  -F "quality=medium" \
  -o invoice-compressed.pdf
```

That's it. One HTTP call. Compressed PDF lands in your working directory.

From Node:

```typescript
import { readFile, writeFile } from 'node:fs/promises';

const file = await readFile('invoice.pdf');
const form = new FormData();
form.append('file', new Blob([file]), 'invoice.pdf');
form.append('quality', 'medium');

const res = await fetch('https://api.convertkr.com/v1/compress-pdf', {
  method: 'POST',
  headers: { Authorization: 'Bearer ckr_live_YOUR_API_KEY' },
  body: form,
});

const buf = Buffer.from(await res.arrayBuffer());
await writeFile('invoice-compressed.pdf', buf);
```

Same pattern in Python, Go, PHP, Ruby — anything with an HTTP client. We don't ship SDKs yet because the API is small enough that a raw `fetch` is shorter than importing a wrapper.

## Why credits, not a subscription

This was the design decision we agonized over.

Most file-conversion APIs charge a flat monthly subscription — say $49/month for up to 1,000 conversions. Sounds clean. But it punishes anyone whose usage isn't perfectly steady.

If you do 100 conversions in January and 2,000 in February, you either overpay in January or get throttled in February. If your business is seasonal (tax software peaks in April, e-commerce peaks in November), subscription pricing doesn't fit. Indie developers shipping side projects hate it most — you pay $49 for the privilege of doing 12 conversions a month.

So we went with credits. Buy a pack up front. Each call deducts a small number of credits based on the operation. Cheap ops cost less, expensive ops cost more. Balance never expires.

| Operation | Credits per call |
|---|---|
| Rotate PDF | 1 |
| Merge / Split PDF | 1-2 |
| Compress PDF | 2 |
| Image convert / resize | 1 |
| HEIC to JPG | 1 |
| PDF to text | 2-3 |
| OCR PDF (when live) | 5-10 per page |

50 credits free on signup, no card. Smallest paid pack is $5.

## Auth — boring, but worth describing

Two modes, one user record:

- **JWT cookies** for the dashboard on `convertkr.com` (signup, balance, generate API keys, view ledger)
- **Bearer API keys** for the API itself — format `ckr_live_<32 hex chars>`

Keys show the full value once at creation. After that we store only the first 12 chars for display and a SHA-256 hash of the rest for verification. Same pattern Stripe uses. We copied it because it's good and there's no point reinventing it.

The credit ledger is **append-only**. We never `UPDATE` or `DELETE` rows — every change is an insert with a positive or negative `delta`. Balance = `SUM(delta) WHERE user_id = ?`. This sounds excessive until you realize how much pain it saves when you need to investigate "why does this user have N credits."

Race-safe credit consumption uses a `pg_advisory_xact_lock(hashtext('user-credits-' || user_id))` inside the deduct transaction, and the deduction is committed only **after** the conversion succeeds. So a failed conversion is a free conversion — no manual refunds, no edge cases.

## "What happens to my file?"

Nothing. Files are never written to disk. Your PDF arrives in the request body, gets processed in worker memory, the response goes back, and the buffer is garbage-collected. There is no "uploads" folder. There is no S3 bucket. There is no temp directory.

This matters more than people realize. If you're processing invoices, contracts, medical PDFs, tax forms — anything sensitive — you don't want a vendor that keeps copies "for 30 days" or "for billing purposes." We don't keep copies at all.

The reason the WordPress side does everything client-side in the browser is the same reason: we don't want to be responsible for your data. The API extends that promise to the server.

## The Office formats sidequest (why they're not in the Node API)

One thing intentionally NOT in the Node API: Word to PDF, Excel to PDF, PowerPoint to PDF.

Honest reason: open-source conversion libraries for Office formats (LibreOffice headless, Pandoc) are *okay* for simple documents but break on real-world files with custom fonts, complex tables, embedded charts, or proprietary Microsoft features. The output looks *almost* right — which is worse than looking obviously wrong. Your customers send the converted file to a recruiter or client, and the formatting is subtly broken.

So Office conversion runs on a separate Windows VPS with actual Microsoft Office installed. Real Word renders real Word files. Same output you'd get if you opened the file in Office on your laptop and clicked "Save as PDF." When those endpoints come online, you'll call them the same way — but they're routed to that Windows worker behind the scenes.

Anyone who tells you their pure-Node service produces "identical to Word" output is selling you something.

## Things we deliberately don't do

This is the part I never see in API docs but always wish I could:

- **We don't store your files.** Already covered. Worth repeating.
- **No webhooks for synchronous operations.** Compress a PDF, get it back in the same HTTP response. No "we'll send a webhook when ready" for jobs that take 2 seconds.
- **No billing for failures.** If conversion fails on our side, no credits deducted. Atomic inside one transaction.
- **No auto-renew.** You buy a pack manually. We don't store your card and surprise you next month.
- **No rate limits as a sales tactic.** Technical limits exist (so one customer can't accidentally DOS the service) but they're high enough that legitimate use never hits them. We're not throttling free-tier users to upsell.
- **No lock-in.** Stop using us — credits stay. Want a refund on unused credits — we'll process it.

## Stack, for the curious

- **Hono** on Node 22 (Express-style ergonomics, web-standards request/response, painless to run on Railway and edge runtimes alike)
- **Drizzle ORM** + **postgres.js** + **PostgreSQL 17** for the user/key/ledger schema
- **TypeScript** strict mode
- **Lemon Squeezy** as merchant of record for payments (we're in Pakistan — direct Stripe isn't available; LS handles VAT and global tax)
- **Railway** for hosting (Postgres + app on git push)
- **Argon2id** for password hashing, **SHA-256** for API key hashing (keys are 128-bit random — slow hashes are unnecessary and would add latency to every request)

The entire codebase is around 3,000 lines of TypeScript. Small on purpose.
